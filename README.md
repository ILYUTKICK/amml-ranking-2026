# AMML ranking competition 2026 — Qwen3-Reranker-4B + LoRA

Финальное решение — одиночный **Qwen3-Reranker-4B**, дообученный с LoRA на обучающих данных соревнования. Измеренный **Public NDCG@10: 0.946752**, validation NDCG@10: **0.9538890735473606**. Это эксперимент **exp005**.

В корне находятся три файла сдачи:

| Файл | Содержимое |
|---|---|
| `solution.ipynb` | Оригинальный выполненный финальный пайплайн: зависимости, данные, препроцессинг, сплит, токенизация, обучение, выбор адаптера, валидация и test-инференс; все outputs сохранены |
| `requirements.txt` | Точные версии прямых и транзитивных зависимостей; платформенные маркеры для macOS и Linux/CUDA |
| `README.md` | Способ запуска, измеренные результаты и история исследования |

Датасеты, обученные веса и токены доступа в публичный репозиторий не включены. Воспроизведение не зависит от доступа к приватному обученному адаптеру: ноутбук обучает новый LoRA-адаптер из исходных предобученных весов.

## Задача и данные

Для каждого запроса заданы кандидаты — текстовые фрагменты. Нужно присвоить каждой паре «запрос — фрагмент» числовой скор и поднять релевантные фрагменты в ранжировании. Отдельного retrieval-этапа нет.

Данные доступны участникам [соревнования](https://www.kaggle.com/competitions/amml-ranking-competition-2026/data):

- `train.csv`: 31 530 пар, 3 042 запроса; бинарная метка `relevance`.
- `test.csv`: 13 507 пар, 1 305 запросов; метки отсутствуют.
- `sample_submission.csv` необязателен; если присутствует, используется его порядок строк.

Результат — `submission.csv` с колонками `id,prediction`. Для каждого запроса кандидаты сортируются по убыванию `prediction`, при равенстве — по возрастанию строкового `id`. NDCG считается на первых `min(10, число кандидатов)` позициях с gain `2^relevance - 1` и discount `1/log2(rank + 1)`, затем усредняется по запросам. Запросы с нулевым IDCG пропускаются реализацией; в используемых train/val таких запросов нет.

Нужны исходные CSV соревнования. Ноутбук вычисляет и выводит их SHA-256; для исходных данных они равны:

```text
train.csv  2c1b26c5d3ee642f2c959b758cea49d4176ca4c0dfe92fbb7236733eff801042
test.csv   4667c49296b72bf64767338c5345cb2f6c7cfbd0671364e5b728d9d5bcc2bf20
```

## Финальный метод

Основа — [Qwen/Qwen3-Reranker-4B](https://huggingface.co/Qwen/Qwen3-Reranker-4B), закреплённая revision **`22e683669bc0f0bd69640a1354a6d0aebcfeede5`**. Готовые веса используются как стартовая точка; дообучение использует только `train.csv` соревнования. Дополнительные открытые датасеты, внешние тексты и псевдометки не используются.

### Препроцессинг и вход

1. Для `query`, `title`, `text`: нормализация Unicode NFC; замена NBSP и удаление soft hyphen/zero-width space; удаление HTML-комментариев.
2. До трёх проходов `html.unescape`; удаление известных HTML-тегов; схлопывание пробелов. Регистр, пунктуация и математические выражения сохраняются.
3. Документ строится из `title` и `text`, с разделителем `. `, если заголовок не заканчивается знаком завершения предложения. Пустой заголовок не добавляется.
4. Документ ограничивается 2 500 символами, затем 284 токенами; запрос — 96 токенами. Используется исходный chat-шаблон токенизатора Qwen с английской инструкцией о релевантности фрагмента запросу. Полная последовательность проверяется на длину не более 512 токенов.
5. Padding выполняется слева. Скоры берутся из логитов следующего токена на последней позиции: **`logit(yes) - logit(no)`**.

Метаданные позиции, источник, ансамбль, стекинг и TTA в финальный скор не добавляются.

### Разделение и обучение

Сплит по `query_id` сохраняет все кандидаты одного запроса в одной части. Для каждого запроса вычисляется SHA-256 строки `42:query_id`; если первые 32 бита, делённые на `2**32`, меньше `0.2`, запрос относится к val.

- Fit: **25 170 строк / 2 428 запросов**.
- Validation: **6 360 строк / 614 запросов**.
- Пересечения запросов между fit и val нет; разбиение записывается в `split.csv`.

| Параметр | Значение |
|---|---|
| Адаптация | LoRA, `r=16`, `alpha=32`, dropout `0.05` |
| Целевые модули | `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj` |
| Loss | Cross-entropy по двум логитам `[no, yes]`, метки 0/1 |
| Оптимизатор | AdamW, learning rate `1e-4` |
| Weight decay | `0.01`, без decay для bias/LayerNorm |
| Scheduler | Linear, warmup 10% шагов |
| Батчи | Microbatch 4, accumulation 8, эффективный batch 32 |
| Нормировка loss | По фактическому числу объектов в окне накопления, включая неполное последнее окно |
| Длительность | Одна эпоха, **787 optimizer-шагов** |
| Seed | 42 для сплита и обучения |
| Precision исходного запуска | Frozen base fp16, LoRA fp32, autocast fp16 и GradScaler на T4 |
| Память | Gradient checkpointing; лучший адаптер сразу сохраняется на диск |
| Validation | Шаги 60, 200, 400, 600 и конец эпохи |
| Выбор модели | Максимальный validation NDCG@10; в измеренном запуске лучший шаг **787** |
| Test inference | Batch 16, исходный raw logit difference, без дополнительного блендинга |

Сохранение лучшего адаптера не копирует всю замороженную 4B-модель в RAM. Перед финальным инференсом освобождаются optimizer state и ссылки на параметры, затем лучший адаптер загружается заново из `best_model/`.

## История исследования

Все validation-результаты ниже относятся к одному исходному query split, кроме специально отмеченных OOF-проверок. Значения — измерения; отсутствующие результаты не заменены прогнозами. Оценка на одном val и подбор по нему не являются полностью независимой оценкой обобщения.

| Эксперимент | Изменение | Validation NDCG@10 | Public | Решение |
|---|---|---:|---:|---|
| exp000 | Константа, порядок по `id`; диагностика на всём train | 0.5737 на train | — | Нижний ориентир |
| exp000 | Ранние фрагменты выше: `-passage_index`; весь train | 0.6470 на train | — | Проверка позиционного сигнала |
| exp001 | Полный fine-tuning BGE-reranker-v2-m3, BCE | 0.937645 | ≈0.9253 | Исходная обученная модель |
| exp004 | Qwen3-Reranker-0.6B, LoRA | 0.912454 | 0.898918 | Уступил BGE |
| exp001 + exp004 | Усреднение скоров с позиционным prior | 0.940029 | 0.927805 | Небольшое улучшение исходного решения |
| **exp005** | **Qwen3-Reranker-4B, LoRA, одиночная модель** | **0.953889** | **0.946752** | **Финальный выбор** |
| exp005 + exp001 | 50/50 после нормализации внутри запроса | 0.957860 | 0.940604 | Прирост val не перенёсся на Public |
| exp006 | BGE, query-balanced pairwise loss + 0.1 BCE | 0.942409 | 0.920694 | Public снизился относительно исходного BGE |
| exp007 | BGE с текстовым префиксом позиции | ≈0.9405 | — | Небольшой прирост val; точное значение доступно только округлённым в логе |
| exp008 | Ещё 80 шагов сохранённого 4B, lr `2e-5` | 0.952779 | — | Уступил исходному адаптеру |
| exp009 | CPU CatBoost поверх 4B: метаданные / лексика / оба набора | OOF 0.950746 / 0.953534 / 0.953757 | — | Все ниже исходного 4B |
| exp010 | Начало + конец длинного документа на сохранённом 4B | 0.949762 | — | Ухудшение |
| exp010 | Фиксированное смешивание 50/50 старого и нового среза | 0.954477 | — | Прибавка +0.000588 не прошла гейт устойчивости |
| exp012 | Ранкер признаков, обученный на исходном fit, малые добавки к 4B | 0.952935 / 0.951484 | — | Оба варианта отклонены |
| exp011 | Тот же 4B-рецепт на 100% train | Не измерено | Не измерено | Только подготовлен; в финальное решение не включён |

exp002/exp003 с дополнительными BGE-сидами были подготовлены; подтверждённые итоговые метрики для них отсутствуют, и в финальное решение они не входят.

### Как контролировался выбор

- Для ансамблей проверялся небольшой фиксированный набор весов. Пятичастная проверка выбора весов по запросам дала изменение относительно одиночного 4B **−0.000166**, интервал query bootstrap примерно **[−0.00546; +0.00517]**. Поэтому максимум на полном val не трактовался как надёжное улучшение.
- В exp009 использовались пять внешних query-folds и три внутренних для выбора рецепта. Внутренний выбор во всех внешних частях оставил исходный 4B. Сам base-checkpoint ранее выбирался на этом val, поэтому это проверка добавленной метамодели, а не полностью независимый тест всего пайплайна.
- В exp012 ранкер признаков обучался только на исходных fit-запросах, без validation labels и нейронных скоров в обучающих признаках. Две заранее заданные добавки не улучшили val.
- В exp010 у 2 647 из 6 360 val-пар документ обрезался; для них проверили другой срез. Для лучшего смешивания интервал изменения составил **[−0.00255; +0.00400]**, а прирост был положительным в трёх из пяти частей. Гейт не пройден; test-инференс пропущен.
- В exp008 и exp010 итоговый fallback-submission совпал с исходным exp005. Повторный Public **0.946752** для такого файла не является результатом новой модели.

### Что выяснилось

Увеличение модели с 0.6B до 4B дало основной подтверждённый прирост. Дополнительные слабые модели, метаданные, продолжение обучения и изменение среза не дали устойчивого улучшения относительно одиночного 4B в проверенных рецептах. Фиксированного смещения между validation и Public не наблюдалось, поэтому прибавки разных методов не складывались в прогноз конечного скора.

Разбор 46 val-запросов с NDCG@10 ниже 0.8 обнаружил отдельные подозрительные случаи разметки: например, в одном запросе о The Sims 3 фрагмент с явным ответом был помечен 0, а фрагмент статьи о дополнении The Sims 2 — 1. Это основание для ручной проверки, а не оценка общей доли ошибок. Метки вручную не исправлялись, индивидуальные test-предсказания по догадкам не редактировались.

## Система обучения и инференса

Измеренный exp005 выполнен на **Linux x86_64**, Kaggle, **Python 3.13.16**, NVIDIA **Tesla T4**, CUDA **12.4**, cuDNN **9.1**, PyTorch **2.6.0**, Transformers **4.51.3**, PEFT **0.15.2**, NumPy **2.1.3**, pandas **2.3.3**. Kaggle выделял T4×2, но код использует только `cuda:0`. Полное сохранённое выполнение заняло около **10 часов**.

`requirements.txt` фиксирует проверенный набор зависимостей для сдачи. Основные версии совпадают с измеренным GPU-запуском; вспомогательные и транзитивные пакеты закреплены при подготовке репозитория. CUDA-библиотеки и Triton отмечены условием Linux/x86_64, macOS-пакет `appnope` — условием macOS.

## Запуск в чистом Linux-окружении

Нужен CUDA-совместимый GPU, интернет для загрузки зависимостей и pretrained-модели, а также исходные CSV соревнования. Для наиболее близкого воспроизведения используйте Tesla T4 и Python 3.13.

```bash
git clone https://github.com/ILYUTKICK/amml-ranking-2026.git
cd amml-ranking-2026
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip check
python -m ipykernel install --user --name amml-ranking --display-name "AMML ranking"
```

Положите `train.csv` и `test.csv` рядом с ноутбуком либо задайте путь к ним в `CFG['data_dir']`. Откройте `solution.ipynb` в Jupyter/VS Code, выберите kernel **AMML ranking** и выполните ячейки по порядку. Код выведет доступность CUDA, версии основных библиотек и хеши данных. Для полного прогона используйте CUDA GPU: CPU-режим предназначен только для уменьшенной проверки.

## Запуск на Kaggle

1. Создайте отдельный notebook и импортируйте `solution.ipynb`.
2. Подключите только данные соревнования с `train.csv` и `test.csv`; путь находится автоматически в `/kaggle/input`. Обученный Output старых экспериментов не требуется.
3. Выберите GPU T4×2 и включите Internet. Убедитесь, что доступно около 10 часов квоты и достаточно времени сессии.
4. Для точного набора версий предварительно установите `requirements.txt` в Python-окружение ноутбука. Первая ячейка дополнительно закрепляет основной ML-стек и проверяет совместимость NumPy/pandas/tqdm. Если после установки обнаружена старая версия основной библиотеки в памяти, перезапустите kernel и выполните заново. Несовместимый необязательный `torchvision` удаляется: решение использует только текст.
5. Запустите через **Save Version → Save & Run All**. Это серверное выполнение не требует открытого браузера или включённого локального компьютера.
6. После успешного завершения проверьте заполненный **Output** и скачайте результаты. Пустая вкладка Output или один только сохранённый исходник не считаются резервной копией артефактов.

## Проверка работоспособности

При подготовке репозитория выполнены:

- установка закреплённых зависимостей в отдельное чистое Python 3.13-окружение и `pip check`;
- проверка формата и синтаксиса `solution.ipynb`, всех 12 номеров выполнения и сохранённых outputs, отсутствия ошибок выполнения и внешних локальных импортов;
- уменьшенный end-to-end CPU-прогон ячеек: реальные CSV и препроцессинг, малые подмножества для обучения/инференса, крошечная случайная Qwen3 с настоящим PEFT LoRA, сохранение и повторная загрузка адаптера, формирование и проверка CSV;
- отдельная проверка реального сохранённого токенизатора и повторный расчёт NDCG@10 по всем 6 360 сохранённым validation-предсказаниям exp005.

**Границы проверки:** CPU-прогон использует уменьшенную модель, токенизатор и данные и не воспроизводит соревновательный скор. Сохранённые outputs корневого `solution.ipynb` относятся к исходному полному успешному Kaggle-прогону; после упаковки репозитория повторное десятичасовое обучение не запускалось. При смене GPU, precision, библиотек и порядка вычислений битовое совпадение нового адаптера и предсказаний не гарантируется. `environment.json` фиксирует основные версии библиотек и систему каждого нового запуска.
